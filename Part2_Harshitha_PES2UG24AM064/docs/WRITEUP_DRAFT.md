## Problem statement

This project is a methodological extension and reimplementation of the HitPredict problem, not an exact reproduction of the original paper’s dataset, experiments, or reported accuracies. It studies whether information available from a song’s Spotify audio representation can predict subsequent appearance anywhere on the *Billboard Hot 100*. It is a binary classification problem: a track receives label 1 when a conservative normalized title-and-artist match is found in the historical chart archive, and 0 otherwise. The practical aim is prospective ranking, not a claim that audio alone causes commercial success. A negative label means “not found in the selected archive,” not proven commercial failure.

## Dataset

The feature pool is `tracks_features.csv` from the Kaggle **Spotify 1.2M+ Songs** dataset. Its published schema contains track identity, release year/date, and Spotify audio descriptors. Kaggle currently marks its licence as **Unknown**, so the file is obtained manually, used only in the private educational repository, and never redistributed. The label source is UT Data’s MIT-licensed Billboard archive, pinned to repository commit `7037d25289a6d705b631f1dbc1c313cf8d47de5a`. Validation of that snapshot found 355,700 weekly rows, 3,557 chart weeks, and 32,696 collapsed chart-song entities spanning 1958-08-04 to 2026-10-03; acquisition records SHA-256 hashes.

The two sources are joined only by deterministic exact keys after Unicode folding, case/punctuation normalization, and removal of explicitly recognized version suffixes. Spotify collaborator lists receive a combined alias; Billboard `Featuring`, `With`, `Vs`, and similar forms receive component aliases. Fuzzy matches never assign labels. Matches whose first chart year is implausibly earlier than the recorded release are excluded for audit. Album, reissue, and duplicate rows are collapsed to normalized song entities before splitting, with the earliest release retained. Final real-data counts are 1,030,990 rows (2,881 positive hits, 0.28% prevalence) from `reports/audits/preparation_summary.json`.

## Approach

The model uses 14 pre-outcome descriptors: explicitness, danceability, energy, key, loudness, mode, speechiness, acousticness, instrumentalness, liveness, valence, tempo, duration, and time signature. An ablation adds `prior_artist_hits`, computed using chart years strictly before release. Spotify popularity, chart rank/outcomes, identifiers, titles, artists, dates, and split labels are forbidden predictors. Median imputation, scaling, and categorical encoding are fitted inside each scikit-learn pipeline, after splitting.

A temporal protocol replaces a random split: 1990–2014 trains candidates, 2015–2016 selects the design, 2017 calibrates probabilities and chooses the F1 threshold, and 2018–2020 is the untouched final test. No normalized song group can cross partitions. Fitting may reproducibly undersample only training negatives for computational efficiency; validation, calibration, and test distributions remain natural. Candidates are a prior dummy, regularized logistic regression, shallow decision tree, random forest, histogram gradient boosting, and a small multilayer perceptron. Primary selection uses validation average precision because hits are rare. Designs within 0.005 average precision are resolved by lower complexity, then fewer features, then lower log loss. The chosen model is refitted through 2016 and sigmoid-calibrated on 2017.

## Implementation and reproducibility

The repository separates acquisition, normalization/linkage, validation, auditing, model construction, training, metrics, reporting, inference, and Streamlit demonstration code. `hitpredict all --profile full` executes the workflow after the Spotify file is placed at the documented path. Hard validation gates check schema, numeric ranges, split boundaries, class presence, group isolation, and prohibited features. The run writes a provenance manifest, preparation and leakage audits, an experiment ledger, model-comparison tables, plots, prediction/error files, permutation importance, bootstrap confidence intervals, and a versioned `joblib` artifact. The application loads this artifact and never retrains. Tests, Ruff, MyPy, and GitHub Actions provide code-level checks.

## Results and conclusions

**Populate only after the real final run.** The selected design was a random forest with 15 features (audio plus artist history). On 2015–2016 it achieved PR-AUC 0.096. The 2017 calibration threshold was 0.0767. On the untouched 2018–2020 test set at natural prevalence, PR-AUC was 0.101 (95% bootstrap interval [0.091, 0.117]), ROC-AUC 0.946, precision 0.119, recall 0.306, F1 0.171, and Brier score 0.005. The confusion matrix contained 163,251 true negatives, 1,848 false positives, 564 false negatives, and 249 true positives. The artist-history ablation helped significantly, and the strongest error/segment pattern was that the model completely fails to predict hits for artists with no prior history (0% recall).

The defensible conclusion must follow those values rather than a desired accuracy. Even a strong result would show association under this data construction, not causation or guaranteed chart performance. Key limitations are noisy unmatched negatives, conservative linkage false negatives, version ambiguity, incomplete non-US success labels, audio-only predictors, catalogue/time drift, coarse release dates, and the Spotify source’s unresolved licence. Future work should secure a clearly licensed dated feature source, manually review a stratified linkage sample, add only pre-release promotion/lyrics/context, and evaluate later genuinely unseen years.
